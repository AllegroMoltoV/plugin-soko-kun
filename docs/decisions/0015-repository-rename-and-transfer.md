# ADR 0015: リポジトリの名前の変更と移管を、リポジトリの ID で追い、所有者の変更は管理者が確かめる

- 状態: 採用 (2026-11-14)

## 背景

本サービスは、登録したプラグインを GitHub の数値のリポジトリ ID で引き直し、名前の変更と移管に追従します。旧い URL は `plugin_aliases` を使って新しい URL へ転送します。

2026-11-14 に、依頼者が 8 本のリポジトリ名を変えたところ、次の問題が起きました。

- 画像の配信が内部の ID ではなく URL の ID で画像を引いており、8 本のロゴと説明の画像が 404 になった (PR #21 で修正済み)
- 名前を変える前に作られた証明は、新しい名前を指定した `gh attestation verify` では検証に通らない。旧い名前を、大文字と小文字の区別まで同じに指定すると通る (speaker-spotlight v1.0.1 で確認)。版の公開から検証までの間に名前を変えると、その版は掲載されない
- 旧い名前で別のリポジトリを登録すると、内部の ID の主キーが重なり、理由の分からない失敗になる。旧い URL の行き先は、現在の名前の一致を旧い名前の記録より優先していた
- 所有者が別のアカウントや組織に変わっても、確認なしに追従していた
- 作者が、名前の変更で何をすればよいかを知る手段が無かった

## 決定

1. プラグインは、これまでどおり数値のリポジトリ ID で追う
2. 同じ所有者のままの名前の変更には、確認なしに追従する
3. 所有者が変わったら、その時刻を記録する。記録がある間は、まだ掲載していない新しい版を管理者の確認待ちにする (乗っ取りの兆候 `owner-changed`)。掲載中の版はそのまま残す。管理者が版を承認したら、記録を消す
4. 旧い URL は、記録した元のプラグインに向け続ける。旧い名前 (別のプラグインの内部の ID か、記録した旧い URL の ID) と同じ名前のリポジトリの登録は、理由のコード `name_reserved` で断る
5. 名前を変えた時点で検証待ちだった配布物のために、旧い名前を大文字と小文字を保って記録する。証明の検証が現在の名前で通らなければ、記録した旧い名前で検証し直す。どちらの場合も、証明書の `sourceRepositoryIdentifier` が登録したリポジトリ ID と一致しなければ失敗とする
6. サイトの登録の方法のページに、名前の変更と移管の節を置き、MCP の説明からこの節を案内する

## 検討した選択肢

| 選択肢 | 採らなかった理由 |
| --- | --- |
| 名前で追う | 作者が名前を変えると旧い名前が空き、そこに攻撃者がリポジトリを作れば、同じプラグインとして扱ってしまう (repo-jacking)。GitHub が空いた名前を保護するのは、人気のあるリポジトリだけ |
| 所有者の変更にも確認なしに追従する | 本サービスが信頼したのは登録した作者で、移管先の別の人の新しい版を確認なしに掲載することになる |
| 所有者が変わったら掲載をやめる | 組織への移管のような正当な変更で、利用者から版が見えなくなる。掲載中の版の中身は変わらないため、止めるのは新しい版で足りる |
| 証明の検証をリポジトリ ID だけで行う | `gh attestation verify` は `--repo` か `--owner` を必須とし、証明書の名前と照合する。ID だけでは呼び出せない。名前で検証したうえで ID を照合する |
| 名前を変えたあとの `list_my_plugins` で旧い ID と新しい ID を返す | 作者の作業は無く、旧い ID のままでも動く。案内の文で足りる |

## 影響

- `plugins` に `owner_changed_at`、`plugin_aliases` に旧い名前 `name` を足す (マイグレーション 0009)。既存の別名の `name` は、現在の所有者名と旧い ID のリポジトリ名から作る
- 管理者の `approve-release` は、`owner_changed_at` も消す
- 検証の受け口の `GET /internal/attestations/pending` は、リポジトリ ID と旧い名前の一覧も返す。`verify.yaml` が変わる
