# ADR 0007: 検査と同期の実行方式

- 状態: 採用
- 決定日: 2026-11-09

## 背景

`submit_plugin` で登録したリリースの配布物は、掲載の前に検査します。VirusTotal の Public API の照会は、1 分あたり 4 件、1 日あたり 500 件に制限されています。配布物の多いリリースでは、1 回の `submit_plugin` の中で照会を終えられません。

同期では、登録済みのプラグインのリリースを定期的に取り直し、新しいリリースや配布物の変化を検出します。要件は、専用のジョブキューや独立したワーカーを導入しないこと、ホスティング環境のスケジュール機能を使うことを求めています。

## 決定

`submit_plugin` では検査を行わず、配布物ごとの検査結果を `pending` で記録して検査待ちとして登録します。照会は Cron Trigger で 15 分ごとに起動する処理で進めます。

同期も同じ Cron Trigger で行います。1 回の起動では、外部呼び出しの予算の中で検査を先に処理し、残りを同期に充てます。OAuth の期限切れデータの掃除も同じ起動で行います。

処理は冪等にします。予算に達したら、残りを次回の起動へ持ち越します。失敗したプラグインの既存の情報は変更しません。

## 検討した選択肢

| 選択肢 | 評価 |
| --- | --- |
| Cron で検査と同期を非同期に進める | 採用しました。構成要素を増やさずに、照会の制限と無料プランの予算に収まります。 |
| `submit_plugin` の中で検査を終える | 照会の制限と、1 回の起動の外部呼び出しの上限を超えます。 |
| Cloudflare Queues などのジョブキューを使う | 要件の YAGNI の方針に反します。Cron で予算の中に収まるため、採用しませんでした。 |
| 検査用と同期用に Cron Trigger を分ける | Cron Trigger の個数はアカウント単位で共有され、残りの個数に余裕がありません。1 個にまとめました。 |

## 影響

登録の直後、プラグインは検査待ちになります。掲載されるのは、Cron で検査が終わり、検査済みのリリースが得られた後です。`submit_plugin` の応答は、検査待ちの状態・詳細ページの URL・検査する配布物の件数を返します。

新しいリリースが検査を終えるまでの間、Web と MCP は前の掲載対象バージョンを示します。

1 日の VirusTotal の照会は、15 分ごとに最大 4 件のとき 384 件になり、上限の 500 件に収まります。予算の値は [検査と同期](../design/scanning.md) に記載します。
