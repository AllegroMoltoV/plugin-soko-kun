# ADR 0019: 第三者の入力に対する検査の原則

- 状態: 採用 (2026-11-23)
- 関係する判断: [ADR 0005](0005-malwarebazaar-not-found-as-clean.md) の未登録の扱い、[ADR 0016](0016-review-by-rules-and-facts.md) の決定 4 (判定しない項目)
- 適用の範囲: 本サービスと、姉妹版の音のプラグイン倉庫くん。姉妹版はこの ADR を派生元として参照する

## 背景

本サービスは、プラグインの作者が用意したリポジトリ・リリース・配布物を検査し、結果から掲載の可否を決めます。検査の入力は、すべて第三者が決められる値です。

2026-11-23 までに、本サービスと姉妹版で検査の穴が続けて見つかりました。修正と配備が済んだものを並べると、次の 3 つの型に分けられます。

| 型 | 事象 |
| --- | --- |
| 分からないものを問題なしとして扱った | 姉妹版の配布物の中身の検査が、危ないパスやアーカイブの外を指すリンクの項目を読み飛ばし、結果を合格のままにした。通信の検出が、検査の候補の列挙に失敗したときに 0 件として扱った |
| 1 件の異常がほかの作者を巻き込んだ | 検査の結果の受け口が、1 つの配布物の不正な値を理由に、ほかの作者の配布物を含む要求全体を拒否した。検証のワークフローが、1 つの版の結果や検証待ちの一覧が大きすぎるときに全体を止め、その版は試行を数えられないまま終わる状態に至らなかった |
| 同じ入力の決まりを 2 か所で別々に書いた | パスの長さの数え方が、検査のスクリプトと受け口で違った。設計書は危ない項目を読まないと定め、審査の基準は判定不能を合格にしないと定め、テストは合格を期待値にしていた |

1 つ目の型では、検査を守るための決まりと、合否の判定が混ざっていました。危ないパスを読まない決まりは正しいものの、読まなかったことが結果に残らず、合格に化けました。

これらの穴は、どれもその時の差分だけを見た修正とレビューのあとに残ったものです。第三者の入力に対する検査の全体に当てはめる原則が無く、変更を照らし合わせる基準がありませんでした。

## 決定

第三者の入力に対する検査は、次の 4 つの原則にしたがいます。

### 原則 1: 分からないものを合格にしない

検査しようとした対象を、読めなかった・解析できなかった・上限で止めた・列挙できなかったときは、合格にしません。結果を判定不能 (`undetermined`) か失敗 (`error`) として記録します。検査を守るための決まりで対象を読まないときも、読まなかったことを結果に残します。

照会が成功し、証拠が見つからなかったときは、合格にしてかまいません。たとえば MalwareBazaar の未登録は、照会が成功し既知のマルウェアに当たらなかったことを示すため、合格です。照会の失敗は合格にしません。

範囲外と決めて調べないことは、この原則の違反ではありません。範囲外にしてよいのは、次の 2 つを両方満たすときです。

- 代わりの検査が残りを覆っている。あるいは、ADR か設計書で範囲外と定めている
- 範囲外であることを、利用者か作者への表示に残す

判定不能で版を止めたときは、作者が原因の項目を特定できる説明を返します。

### 原則 2: 異常をその対象に閉じ込め、必ず終わる状態に至らせる

1 つの配布物や版の異常は、その配布物や版の結果にだけ反映します。ほかの配布物・版・作者の結果を変えてはいけません。要求の全体を拒否してよいのは、認証・識別子・重複・件数のように、要求の形そのものが壊れているときだけです。

検査の結果は、次のように必ず終わる状態に至らせます。

| 結果 | 終わり方 |
| --- | --- |
| 判定不能 | やり直しても同じ結果になるため、その時点で作者の待ちとする |
| 第三者の入力に起因する失敗と、原因を特定できない失敗 | 試行を数え、上限に達したら管理者の待ちとする。タイムアウト・5xx・形の合わない応答は、その場では原因を第三者の入力と一時的な障害に切り分けられないため、ここに含める。一時的な障害で上限に達した版は、管理者が検証をやり直せる |
| 運営側の資源の不足 | 内部のコードなどで特定できる、支出の上限・無料枠の不足・混雑・GitHub のレート制限・予算の超過による失敗は、作者の責任ではないため試行に数えず、後でやり直す。待ちの一覧に溜まることで、管理者が気づけるようにする |

### 原則 3: 入力の決まりを 1 か所で定める

第三者の値を受け入れる決まりは、値を作る側と受ける側で同じ定義を使います。決まりには、パスの形と長さ、名前、件数、大きさ、許す値の一覧を含みます。作る側は検査のスクリプト、受ける側は検査の結果の受け口です。

言語が違うために定義を共有できないときは、片方を正本とし、もう片方とのずれをテストで検出します。設計書・審査の基準・テストの期待値も、同じ定義に合わせます。

### 原則 4: 第三者が決められる値を一覧にする

第三者が決められる値の一覧を、設計書に置きます。一覧には、値ごとに次の 3 つを書きます。

- 値の名前
- 決まりを外れたときの扱い。原則 1 と原則 2 にしたがう
- 決まりと上限の正本の所在

決まりと上限の数値は一覧に写しません。写すと、原則 3 が避ける 2 か所目の定義になるためです。新しい値を扱う変更では、一覧も更新します。

### レビュー

マージの前のレビューでは、変更がこの 4 つの原則にしたがうことを確かめます。

## 検討した選択肢

| 選択肢 | 判断 |
| --- | --- |
| 共通の原則を ADR で定め、検査の全体に当てはめる | 採用しました。変更とレビューを照らし合わせる基準ができます。両方のサービスの検査を同じ基準で監査できます |
| 見つかった穴を個別に塞ぐ | 採用しませんでした。同じ型の穴が、別の検査で続けて見つかっています |
| 検査ごとに原則を定める | 採用しませんでした。3 つの型は検査をまたいで現れており、検査ごとの定めでは同じ型の見落としが残ります |

## 影響

判定不能で止まる版が増えます。正規の配布物を止めることもありえます。止めたときの説明が作者に届くことを、原則 1 の一部として確かめます。

既存の検査は、この原則に照らして監査します。範囲外と決めて調べない既存の検査は、原則 1 の 2 つの条件を満たすことを確かめます。

原則 4 の一覧は、新しく作る必要があります。
